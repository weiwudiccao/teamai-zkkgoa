# Capacity safe-cleanup decision notes

Date: 2026-08-31
Scope: project
Tags: capacity, safe-cleanup, server-ops, backups, docker

## Summary

For repeated server-capacity checks and cleanup requests, do not rely on old screenshots or prior chat results. Capacity can change quickly because temporary screenshots, logs, build cache, and backup directories can regrow between turns.

Use the project's standard capacity-report workflow immediately before cleanup and again after cleanup. Treat the fresh report as the only current source of truth.

## Default safe-cleanup boundary

When the user says "safe cleanup", keep the scope narrow unless they explicitly approve more.

Safe by default:

- old project temporary directories
- generated temporary screenshot files
- container JSON logs
- build cache
- bounded system journal cleanup
- old backup directories only when a cutoff time or exact backup class has been approved

Not safe by default:

- databases
- live source trees
- current frontend static assets
- Docker volumes
- Docker images
- protected migration or original-path backup records

## Backup handling

Production backups should go to the dedicated backup disk or backup mount when one exists. Cleanup logic must distinguish real backup directories from compatibility links or protected migration records. Protected original-path records must be preserved.

Before deleting broad backup candidates, print the matched list, count, and estimated size. Prefer a dry-run first when the match rule is broad.

## Docker handling

Docker often remains a large pressure point after default cleanup. Reclaimable image size shown by Docker is only a candidate, not authorization.

Only clean Docker images after separate user approval. Never clean Docker volumes without a specific review proving they are unused and disposable.

## Regenerating temporary screenshots

If temporary screenshot files keep reappearing, treat one-time deletion as temporary relief. Identify the producing service or automation and add a retention policy, such as scheduled deletion of old generated files, while leaving the service running unless the user approves a service-level change.

## Reporting pattern

After every cleanup, report:

- fresh before and after capacity
- exact cleanup scope
- approximate count and size removed
- protected areas that were not touched
- remaining high-usage areas and whether they need separate approval

This prevents accidental expansion from low-risk cleanup into database, source, Docker image, or Docker volume deletion.
